■ UI 설계 의도
  이 화면은 아이가 아니라 "옆에 앉은 부모"가 보는 화면입니다.
  부모의 문제는 하나뿐입니다 — 지금 아이가 뭘 만지고 있는지, 뭘 도와줘야 하는지 모른다.

  · 히어로 = 가상 닷패드
    실물 배치 그대로 화면에 그렸습니다.
      여러 줄 점자 칸(60×40 핀) / 세모 버튼 2 + 길쭉한 동그라미 버튼 4 / 한 줄 점자 칸(20셀)
    올라온 핀은 빛나는 금색, 내려간 핀은 어두운 점입니다.
    아이 손끝의 상태가 그대로 보입니다.

  · 눌러야 할 버튼이 빛납니다
    질문이 나오면 답할 수 있는 버튼에 불이 들어옵니다.
    13페이지 "네 번째 동그라미 버튼을 눌러볼래?" 에서 부모가 어디를 짚어줘야 할지 즉시 압니다.
    이게 이 화면의 실질적 존재 이유입니다.

  · 닷패드가 말풍선으로 이야기합니다
    아바타는 핀으로 그린 얼굴이고 표정이 바뀝니다(기본/기쁨/응원).
    설계서 v0.2 §3.2 "닷패드가 스스로 얼굴을 그린다" 를 그대로 구현했습니다.

  · 스티커는 실제 촉각 자산에서 그렸습니다
    5.dtm 동그라미, 4.dtm 세모, 7.dtm 채워진 세모, 3.dtm 네모, 15.dtm 채워진 동그라미.
    DTMS 핀 데이터를 디코딩해 바운딩 박스를 잘라 점으로 다시 그립니다.
    새로 그린 그림이 한 장도 없습니다.

  · 진행 표시는 막대가 아니라 핀 27개입니다
    지나온 페이지는 채워지고 현재 페이지는 금색으로 떠오릅니다.

  · 팔레트
    옅은 라일락 종이(#EDEAF6) / 자두빛 잉크(#241C3B) / 기기 본체(#2F2550)
    올라온 핀 = 금색(#FFC24D) / 주 동작 = 포도색(#5B3FD6) / 정답 = 민트(#12A06A)
    "올라옴"을 빛으로 표현하려고 어두운 기기 위에 금색 핀을 얹었습니다.

  · 정답은 화면에 절대 표시하지 않습니다
    부모용 코칭 문구(parentCoach)와 "아이에게 물은 것"만 보여주고,
    답을 찾기 전까지 "정답은 알려주지 마세요" 를 띄웁니다.

■ 실제 헤드리스 브라우저 QA (사용자 리포트: "여전히 보라색/이상한 서비스 같다")
  이번엔 코드를 읽고 "됐다"고 말하는 대신, 실제로 Chromium을 띄워 렌더링 결과를 확인했습니다.

  1) 보라색 화면 재현 안 됨 — 원인은 캐시/구버전 폴더로 추정
     전달드린 파일을 직접 서버로 띄워 computed style을 찍어보니 --page:#FBF7EE,
     --accent:#C43D00 등 전부 정상 반영돼 있었고, 스크린샷도 웜 크림 톤으로 나왔습니다.
     즉 전달된 파일 자체는 문제가 없었고, 브라우저 캐시 또는 예전 dotbuddy 폴더를
     덮어쓰지 않은 상태를 보고 계셨을 가능성이 높습니다. 폴더를 통째로 지우고
     새 zip을 다시 풀어서, 시크릿 창으로 열어 확인해 주세요(캐시 완전 배제).

  2) ★ 발견한 진짜 버그 — TTS 무응답 시 앱 전체가 영구히 멈춤 (심각)
     구조: 내레이션 음성 종료(onEnd) → 질문 문구 음성 종료(onEnd) → 그제서야 답변 버튼이 열림.
     이 콜백 체인이 전부 TTS 성공에 의존하고 있었습니다.
     서버 음성이 실패하면 브라우저 자체 음성(speechSynthesis)으로 폴백하는데,
     음성 엔진이 설치 안 됐거나 응답이 없는 환경(정확히 이 QA 샌드박스가 그런 상황)에서는
     onEnd가 영원히 안 불려 27페이지 중 질문이 있는 16페이지 전부가 멈췄습니다.
     실제 자동 순회 테스트로 재현: 6초 대기해도 단 한 페이지도 답변 버튼이 안 열림.
     → 화면이 아무 반응 없이 멈춰 있는 것 자체가 "이상한 서비스"라는 인상의
       실질적 원인이었을 가능성이 있습니다(테마 색상과는 별개로).

     조치: 음성 길이에 비례한 안전장치 타임아웃(최소 4초 · 최대 12초)을 추가해,
     TTS가 어떤 이유로든 응답하지 않아도 반드시 다음 단계로 넘어가게 했습니다.
     순수 로직 단위 테스트로 검증:
       · TTS 완전 무응답 + 60자 텍스트 → 9000ms에 정확히 복구 (PASS)
       · 아주 짧은 텍스트 → 최소 바닥값 4000ms 적용 (PASS)
       · 아주 긴 텍스트 → 최대 상한 12000ms 적용 (PASS)
       · 정상 응답하는 TTS → 안전장치가 지연을 추가하지 않음, ~50ms 그대로 (PASS)
     실제 페이지 콘텐츠로도 재확인: 6·7·8·11·13·15·16·18·19·22·23페이지가
     410ms~5.6초 사이에 정상적으로 답변 버튼이 열리고, 스티커·별가루가 실제로 적립됨을 확인.

  3) 부수 발견 — 말하는 동안 화면에 아무 시각적 신호가 없었음
     상태 안내가 스크린리더 전용(aria-live)이라, 안전장치 덕분에 최대 12~20초 정도
     기다려야 할 수 있는 구간에서 눈으로 보는 부모에게는 아무 표시가 없었습니다.
     "닷패드" 라벨 옆에 "● 말하는 중" 표시를 추가해, 대기 중에도 화면이 멈춘 게
     아니라 진행 중임을 보이게 했습니다.

  4) ★ 실제 접근성 버그 — 대비 미달 (닷 디자인시스템 적용 과정에서 발생)
     .pill 기본 상태와 .gate 안의 code 태그가 accent(#C43D00) 텍스트를
     accent-tint(#F7E4D8) 배경 위에 올렸는데, 계산해보니 4.25:1로 WCAG AA(4.5:1) 미달.
     accent-dark(#A83400)로 교체해 5.40:1로 통과 확인.

  5) 대비 전수 검사(참고): coachText/bubbleLine 16.77:1, btn-go 5.23:1 — 전부 여유있게 통과.
     .hint 텍스트는 스크립트 버그로 일시적으로 "실패"라고 잘못 측정됐던 것을
     직접 계산으로 재확인(실제 4.90:1로 통과, 그라디언트 배경을 투명으로
     오인식한 테스트 스크립트 쪽 오차였음 — 참고용으로 기록).

  QA 방법: puppeteer-core + @sparticuz/chromium(번들 바이너리, 외부 CDN 다운로드 없이
  npm 레지스트리만으로 설치 가능해 이 환경에서 헤드리스 브라우저 확보) 로 실제 렌더링·
  27페이지 자동 순회·인터랙션 시뮬레이션·contrast 계산·타임아웃 단위 테스트를 수행.

     배경을 제거해 진짜 알파 채널을 만들었습니다.
  2) 자산 최적화

■ .dtms / .dtma / .dtm 다중 업로드 + 실제 음성 재생 지원
  헤더 조작 바에 "다른 자료 불러오기" 버튼 추가 — 오류 상황이 아니어도 언제든
  누르면 파일 선택창이 열립니다. 여러 파일을 한 번에 선택할 수 있습니다.

  · 본문 파일 판별: 확장자(.dtms/.dtma)와 무관하게 JSON을 파싱해 items[] 배열이
    있으면 본문으로 인식합니다. .iact.json 형태(pages 객체)를 가진 파일은 자동으로
    interaction 사이드카로 인식합니다.
  · .dtm 자산: 본문에서 graphic.data가 비어 있고(전부 0) graphic.name이 있는 페이지에
    한해, 같은 이름의 업로드된 .dtm 파일에서 그래픽을 가져옵니다. 이미 데이터가
    내장된 페이지(현재 기본 콘텐츠가 그렇습니다)는 건드리지 않습니다.
  · 오디오: audio.fileName과 이름이 일치하는(확장자가 달라도 매칭되도록 처리 — 예:
    DTMS엔 narration2.mp3로 적혀 있는데 실제로는 .wav로 올려도 이름만 같으면 매칭)
    업로드 파일을 찾아 실제 재생합니다.

  ⚠️ 정직하게 밝혀둘 점: .dtm 단일 파일과 .dtma의 정확한 내부 스키마를 실물로
  확인하지 못했습니다.
    · .dtm은 "순수 600자리 헥스 텍스트" 또는 "{data:...}"/"{graphic:{data:...}}"
      형태의 JSON, 둘 다 시도하도록 방어적으로 구현했습니다. 합성 테스트 파일로는
      정상 동작을 확인했지만, 실제 파일 구조가 다르면 알려주세요.
    · .dtma는 .dtms와 같은 items[] 스키마라고 가정했습니다. 실제 파일을 하나
      받으면 파서를 그에 맞춰 정확히 조정하겠습니다.

  음성 재생 우선순위(Voice 어댑터, §5.1 안전장치와 동일한 구조 위에 확장):
    실제 오디오 파일 있음 → 그 파일 재생, 실패 시 TTS로 자동 전환
    오디오 파일 없음      → 기존과 동일하게 TTS(+ 무응답 시 4~12초 안전장치)
    오디오 파일 재생의 안전장치는 길이를 미리 알 수 없어 고정 20초 상한을 씁니다.

  검증: 합성 .dtma(items 2개, 1페이지는 그래픽 이름만 있고 데이터 비어있음,
  2페이지는 audio.fileName 지정) + 외부 .dtm(600자리 순수 헥스) + 오디오(.wav,
  DTMS엔 .mp3로 기재) 세 파일을 헤드리스 브라우저로 동시 업로드해 종단 검증.

  실제 blob URL로 연결됨을 확인. 확장자 불일치 매칭도 정상 동작.

■ .dtma 실제 구조 확정 — ZIP 바이너리였습니다 (이전 턴 수정)

  ⚠️ 여전히 확인 필요: zip 내부의 정확한 파일 배치(파일명 규칙, 폴더 구조)는

  검증: JSZip으로 직접 만든 실제 구조의 .dtma 픽스처(content.dtms + audio/v1.wav
  폴더 중첩, DTMS엔 v1.mp3로 기재)를 헤드리스 브라우저에 업로드해 종단 검증 완료 —

  동그라미/세모/네모라는 도형 이름을 그대로 가져다 쓰고 있어 뭉뚱그려진 느낌이
  있었습니다. p8·p21(4방 도형 게임)의 "네모"는 실제 도형 이름이라 그대로 두고,
  기기 부품을 가리키는 p2("넓은 네모")·p15("길쭉한 네모")만 "네모판"으로 교체했습니다.
  text.plain·text.data·graphic.data 전부 liblouis ko-g1 파이프라인으로 재생성했고,
  interaction 사이드카의 관련 prompt·promptChild·onNo.say도 함께 맞췄습니다.
  변경 후 DTMS 전체에서 "네모" 재검색 — p8·p21(도형 이름)만 남고 p2·p15는
  전부 "네모판"으로 확인됨. 27페이지·그래픽 600자 무결성 유지, 헤드리스
  브라우저로 p2 렌더링 확인 완료.

■ 완료 리포트 화면 (신규) — "부모·교사를 위한 와우 포인트"
  요청 배경: 닷패드 미리보기 외에 사이트 시각적 UI에서 학부모·교사가 좋아할 만한
  포인트가 필요하다는 요청. 후보 3개(완료 리포트/점자 눈으로 확인하기/학습 지도)
  중 "완료 리포트"를 우선 선택하셨습니다.

  기존엔 27개 이야기를 다 마쳐도 "오늘 여정을 모두 끝냈어요"라는 말풍선 한 줄이
  전부였습니다. 그 성취의 증거(스티커·별가루·정답률)가 화면 어디에도 정리돼
  보이지 않았다는 게 가장 큰 공백이었습니다.

  구성: 점프 GIF(축하) · 통계 칩 3개(이야기 수·질문 정답/전체·걸린 시간) ·
  게이트 화면의 점-하트 시그니처를 그대로 재사용한 메달리온 · 모은 스티커
  진열(기존 컴포넌트 재사용) · 정답률 기반 코멘트 · 다시 보기/처음부터 다시
  하기 버튼. 새로 그린 요소가 거의 없고 전부 기존 자산 재조합입니다 —
  "모듈화" 원칙에 맞게 이미 검증된 컴포넌트(스티커 렌더러, 메달리온 SVG,
  버튼 클래스)를 그대로 가져다 썼습니다.

  세션 통계 신규 추적: session.startedAt(시작 시각)·answered(정답 수)·
  firstTry(한 번에 맞힌 수) — 지금까진 어디에도 기록되지 않던 값입니다.
  정답률 85% 이상 "질문에 척척 답했어요!", 50% 이상 "차근차근 잘 배웠어요!",
  그 미만 "천천히, 그래도 끝까지 해냈어요!"로 코멘트가 갈립니다(항상 격려
  톤 유지 — 낮은 점수를 지적하지 않음).

  트리거 지점 두 곳: ① 마지막 페이지에 질문이 있고 정답을 맞혔을 때(onCorrect
  내부) ② 마지막 페이지가 질문 없는 순수 내레이션(현재 27페이지가 이 경우)일
  때 내레이션 재생이 끝나는 시점(afterNarration 내부). 원래 코드는 ②를
  전혀 처리하지 못해 지금 콘텐츠 기준으로는 리포트가 뜰 방법이 없었습니다.
  session.reportShown 플래그로 재방문·다시 듣기 시 중복 등장 방지.

  접근성: role=dialog/aria-modal, Esc로 닫기, 열릴 때 첫 버튼에 포커스,
  모달이 열려 있는 동안 배경 키보드·닷패드 버튼 입력 차단(첫 연결 놀이와
  동일한 가드 패턴 재사용).

  검증: 헤드리스 브라우저로 마지막 구간(23→24→25→26→27)을 직접 진행시켜
  리포트 등장·통계 계산·스티커 표시·재시작 버튼 동작까지 전부 확인.
